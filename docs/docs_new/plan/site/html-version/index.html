OandOcraft Overhaul Plan

_Last updated: 2026-05-02_

`docs_new/plan` is the active planning home for the OandOcraft overhaul. It is the canonical root for the rewrite, the phase files, the HTML presentation, and the supporting plan-site material.

This is not a historical note. This is the working plan that governs the rewrite.

Purpose#

This plan exists to replace scattered legacy planning with one execution-ready source of truth.

It defines:

  • the product direction
  • the current repo truth
  • the boundaries between current and future stack decisions
  • the agent workflow expected for all structured work
  • the phase-by-phase path from cleanup to rollout

If a change is not consistent with this plan, the change is not ready.

Operating principles#

1. Truth before ambition

Do not describe the repo as something it is not. The plan must reflect the actual codebase, not a desired future state written as if it were already done.

2. Smallest complete change

When implementing work from this plan, choose the smallest change that satisfies the phase goal while preserving compatibility and clarity.

3. Explicit decisions over implied assumptions

If a detail matters to architecture, routing, security, rendering, or deployment, it must be written down explicitly.

4. Source of truth wins

When documents conflict, the current repo truth and this canonical plan override older references.

5. Reviewable work only

Any request or implementation should be explainable, testable, and reviewable without hidden behavior.

Working method#

Use the three-agent workflow for all structured work.

Planner first

The planner is responsible for framing the work before code or content changes begin.

  • define the objective in one sentence
  • identify the source of truth
  • bound scope, assumptions, dependencies, constraints, and non-goals
  • specify validation, risks, and acceptance criteria
  • decide which phase owns the work
  • produce an execution-ready plan
  • end with a concrete handoff to the builder

Builder second

The builder implements only the approved scope.

  • implement only the requested work
  • fail closed on ambiguity or missing decisions
  • keep changes minimal and source-of-truth aligned
  • preserve existing structure unless the request explicitly changes it
  • keep compatibility unless a migration is explicitly planned
  • stop and report blockers instead of inventing details

Critic last

The critic reviews only.

  • compare work against the request, the plan, and the source of truth
  • identify contradictions, missing details, boundary violations, and hardcoding
  • confirm that the implementation matches the approved phase
  • require explicit corrections for failures
  • remain read-only at all times

Stack and truth#

Current stack truth

  • The current app shell is Vite + React.
  • index.html loads /src/main.tsx, which is the current runtime entry.
  • The current docs and plan must not describe the repo as already migrated to Next.js.
  • Route behavior, editor behavior, and persistence behavior must be described as they exist now, not as they might exist later.

Future desired stack

  • If the main site later moves to a different stack, that is a future decision, not current truth.
  • Any future stack decision should be documented separately from the current repo truth.
  • The current app should never be described as a migrated Next.js system unless the entrypoint actually changes.

Repo truth that must stay stable

  • Public routes: /, /login, /signup, /forgot, /auth/verify, /auth/reset, /help, /docs.
  • Auth routes: /onboarding/team, /account.
  • Office routes: engine, map, pixi, roster, reports, reports/scenarios, org-chart.
  • RequireAuth sends unauthenticated users to login with next.
  • RequireTeam sends zero-team users to onboarding.
  • useCan(action) remains the explicit permission gate.
  • Autosave stays debounced.
  • Optimistic locking stays the default save strategy.
  • Conflict handling must stay explicit.
  • Payload compatibility should be preserved unless a migration is intentionally scoped.

Non-negotiable documentation rule: If a doc describes the current repo truth, it must match the live runtime and the actual route model. If a doc describes a future target, it must label it as future target language.

How to use this plan#

  1. Start from this plan, not from archived reference docs.
  2. Check the repo truth before making architectural assumptions.
  3. Confirm whether the change belongs in Phase 1, Phase 2, or Phase 3.
  4. Make the smallest change that still respects the phase goal.
  5. Validate that Markdown and HTML still match after every meaningful update.
  6. If the work crosses a phase boundary, stop and reframe the task before implementing.

Flow of execution#

[Start] | v [Read this plan] | v [Check repo truth and stack] | v [Planner: structure the work] | v [Builder: implement the approved scope] | v [Critic: verify against rules] | v [Phase 1: foundation + truth + archive hygiene] | v [Phase 2: catalog generation + validation + internal deployment] | v [Phase 3: external rollout + renderer evolution] | v [Validate Markdown + HTML] | v [Deliver]

What the product should become#

The target is a serious internal operations platform with three strong surfaces:

  1. Workspace editing — fast, clear, keyboard-friendly daily work.
  2. Admin control plane — permissions, workspace settings, policy, audit, and oversight.
  3. Rendering and spatial engine layer — map, Pixi, and future 2.5D / 3D experiences as first-class product decisions.

The product should feel cohesive, deliberate, and professional. It should be easier to operate than before, not just more technically flexible.

UX / UI vision#

Primary UX goals

  • Make the interface easier to scan and harder to misuse.
  • Reduce visual noise and keep actions grouped by intent.
  • Support dense operational data without overwhelming users.
  • Make state, selection, and permission boundaries obvious.
  • Keep the editor responsive and predictable.
  • Ensure important operations are discoverable without adding clutter.

UI principles

  • Clear hierarchy over decoration.
  • Persistent context over hidden state.
  • Fast editing over modal-heavy flows.
  • Strong empty, loading, and error states.
  • Power-user efficiency without losing clarity.
  • Role-aware visibility instead of generic one-size-fits-all screens.

Surface intent

  • Map / workspace: sharp, immediate, controllable.
  • Roster / reports / org chart: operational views, not generic dashboards.
  • Admin screens: explicit, structured, role-aware.
  • Engine chooser: a real product decision point, not a debug menu.
  • Help and docs: support the workflow, not distract from it.

Engine, Pixi, and 2.5D / 3D direction#

Current direction

  • engine remains the route-level chooser.
  • map remains the production editor path.
  • pixi remains a separate rendering surface, not a sub-mode of map.
  • Each rendering route should have a clear job and a clear exit criteria.

What we want next

  • Treat Pixi as a high-potential renderer path for performance, fidelity, and advanced interactions.
  • Keep room for richer spatial representation beyond flat 2D.
  • Let 2.5d be the step between today’s editor and deeper spatial rendering.
  • Preserve the ability to have distinct rendering strategies for different workflows.
  • Avoid collapsing everything into one rendering implementation just because the UI can technically support it.

Product decision rule

If a rendering change improves realism, performance, or operator clarity, it belongs in the engine plan. If it only changes appearance inside one editor state, it stays in the editor plan.

Admin control plane#

The overhaul should make admin and workspace control feel intentional.

Must support

  • Workspace settings and configuration
  • Permission and role-aware controls
  • Audit and oversight paths
  • Safe destructive actions with obvious guardrails
  • Distinction between daily editing and privileged operations
  • Clear ownership of who can do what and where those actions live

Design requirement

Administrative actions should not be buried inside unrelated screens. They should live in a coherent control plane that is obvious to operators and safe for team members.

UX requirement

Admin views should explain consequences before actions are taken. Destructive or high-risk actions must be isolated, labeled clearly, and reversible where possible.

Phase model#

The phase model below defines the current rewrite path.

Phase 1 — Foundation, truth, and archive alignment

Purpose:

  • establish the single source of truth
  • reconcile documentation with the repo
  • move obsolete material into the archive
  • make the plan and HTML mirror each other
  • enforce the planner / builder / critic workflow

Success looks like:

  • no ambiguity about the current stack
  • no ambiguity about canonical docs
  • no confusion between current truth and future targets
  • a plan that is detailed enough to guide execution

Phase 2 — Generated catalog, workflow validation, and internal deployment

Purpose:

  • make the catalog coherent and generated
  • validate real operator workflows
  • harden behavior around selection, editing, and recovery
  • deploy internally before any broader rollout

Success looks like:

  • real workflows can be completed end to end
  • the catalog model is understandable and extensible
  • internal users encounter the real gaps before external users do

Phase 3 — External rollout, renderer expansion, and 2.5D / 3D direction

Purpose:

  • evolve the rendering strategy outward
  • prepare the product for a broader audience
  • support richer spatial presentation when it helps the workflow
  • keep the renderer architecture deliberate instead of accidental

Success looks like:

  • a stable outward-facing experience
  • rendering strategy choices are explicit
  • 2.5D and 3D are treated as product decisions, not gimmicks

Detailed phase plan#

Phase 1 — Foundation, truth, and archive alignment

Goal: establish the only source of truth, remove ambiguity, and prepare the plan set so future work can proceed without guessing.

Outcome: the team knows what is active, what is archived, what the stack really is, and what decisions are already fixed.

Dependencies: repository truth, current docs state, archive inventory, plan ownership, agent pack in .cursor/agents/.

Owner type: product lead, platform lead, docs owner, and reviewer.

Exit gate: no implementation work starts until the plan, HTML, and source truth agree.

1.1 Canonical plan ownership

  • Confirm docs/docs_new/plan/OandOcraft_PLAN.md is the active working plan.
  • Confirm docs/docs_new/plan/OandOcraft_PLAN.html is the matching published view.
  • Keep both files in lockstep whenever one changes.
  • Remove wording that implies any other plan is active.
  • Confirm the root AGENTS.md and .cursor/agents/AGENTS.md point to the same workflow.
  • Ensure the three-agent pack is the standard operating model for structured work.

1.2 Stack truth and migration boundaries

  • Record the current app shell as Vite + React.
  • Record index.html → /src/main.tsx as the current runtime entry.
  • Record Next.js + React as the future main-site target only.
  • Keep current editor-runtime truth separate from future site migration truth.
  • Remove any phrase that makes the repo sound already migrated.
  • Preserve the distinction between current editor architecture and future site architecture.

1.3 Route and permission truth

  • Keep the route inventory explicit and current.
  • Preserve the auth and office route separation.
  • Preserve the RequireAuth and RequireTeam behaviors.
  • Preserve useCan(action) as the explicit permission gate.
  • Preserve autosave, optimistic locking, explicit conflicts, and payload compatibility.
  • Document any future route changes only as proposals, not as current truth.

1.4 Archive inventory and reference hygiene

  • Identify every non-canonical reference document still in working folders.
  • Move obsolete reference docs out of the active planning path.
  • Keep the archive clearly labeled as historical, not active.
  • Preserve OandOcraft_BLOCK_LIBRARY_SOURCES.md as the explicit exception.
  • Note which archived docs may be consulted for context and which may not.
  • Prevent archived docs from being cited as live truth in future work.

1.5 Documentation alignment

  • Make the Markdown plan and HTML plan say the same thing.
  • Keep section order, headings, and intent aligned.
  • Rewrite vague summary text so it becomes implementation-grade language.
  • Remove duplicated or circular statements.
  • Ensure the plan can be used as a source of truth by future agents.
  • Make the HTML version read like a polished docs page, not a marketing page.

1.6 Phase 1 validation and acceptance criteria

  • A builder can identify the current stack without guessing.
  • A builder can identify the future stack target without confusing it for current truth.
  • A reviewer can tell which files are canonical and which are archival.
  • A builder can understand the agent workflow from the plan.
  • HTML and Markdown remain aligned after edits.
  • No stale reference layer is presented as active.

1.7 Phase 1 risks

  • Stack confusion leaks into implementation work.
  • Archived docs continue to behave like live docs.
  • The plan remains too vague for execution.
  • The HTML diverges from the Markdown source of truth.
  • The agent workflow is described loosely instead of operationally.

Phase 2 — Generated catalog, workflow validation, and internal deployment

Goal: build the first usable generated catalog, validate real workflows, and deploy internally before any external rollout.

Outcome: the product can be used by internal operators with enough confidence to expose workflow gaps and catalog issues.

Dependencies: Phase 1 complete, stable object schema decisions, archive boundaries set, route truth stable, agent workflow active.

Owner type: product, design, frontend, content/system owner, and reviewer.

Exit gate: internal users can run the product on real work with minimal hand-holding.

2.1 Catalog definition and object taxonomy

  • Define the initial object families that the catalog must support.
  • Separate core objects from temporary placeholders.
  • Define which objects must exist on day one for a usable workspace.
  • Define naming rules for generated assets so future additions stay coherent.
  • Define dimension, category, and display-rule requirements.
  • Define what metadata every catalog object must carry.
  • Define which objects can later become photo-backed without changing the schema.
  • Define which objects are intentionally temporary and why.

2.2 Generated asset preparation

  • Produce the initial generated 2D assets needed for the first usable catalog.
  • Define how 2.5D assets are derived from the same object metadata.
  • Decide which elements are visual tokens versus semantic objects.
  • Validate that generated assets do not depend on hardcoded per-shape logic.
  • Ensure the generated set covers common layouts, common furniture, and common annotations.
  • Ensure the generated set is sufficient for a real internal workflow, not just a demo.

2.3 Editor workflow validation

  • Validate object placement, drag, drop, snap, align, resize, select, and inspect.
  • Validate duplication, deletion, multi-select, and group operations if supported.
  • Validate undo, redo, autosave, and conflict recovery.
  • Validate search, filter, and library browsing inside the catalog.
  • Validate that selection and state feedback are obvious.
  • Validate that keyboard workflows remain usable for power users.
  • Capture where the editor is slow, confusing, or brittle.

2.4 Internal deployment design

  • Decide which internal user groups receive the first deployment.
  • Define the internal deployment environment and its expectations.
  • Define what production-like behavior must be preserved.
  • Define what telemetry or feedback should be collected.
  • Define how internal users will report workflow failures.
  • Define what counts as a blocker versus a cosmetic issue.

2.5 Internal deployment execution

  • Deploy the generated catalog to internal users only.
  • Verify routes, permissions, and access boundaries in the deployment.
  • Observe real usage patterns.
  • Record where users hesitate, make mistakes, or need help.
  • Record which objects or workflows are missing from the catalog.
  • Keep the environment close to production behavior.

2.6 Phase 2 validation and acceptance criteria

  • The first generated catalog is usable in real workflows.
  • The internal deployment exposes the real interaction gaps.
  • Users can perform daily tasks without hand-holding.
  • The catalog model is stable enough to continue growing.
  • The data model can later support photo-backed and 3D phases.
  • The plan can describe what the next rollout needs to fix.

2.7 Phase 2 risks

  • The catalog is too small to expose real workflow problems.
  • Generated assets are too generic to test meaningful usage.
  • The internal deployment still feels like a demo.
  • The object model is too unstable to carry into later phases.
  • Workflow validation is delayed because the catalog is overdesigned.

Phase 3 — External rollout, renderer expansion, and 2.5D / 3D direction

Goal: release outward with a stronger spatial and rendering story once the internal system is proven.

Rough timeframe: 4–8 weeks if the internal build is already solid; longer if the renderer and catalog integration needs more refinement.

Dependencies: Phase 2 validation, stable catalog data, internal deployment feedback, renderer strategy.

Owner type: frontend/rendering, product, and release owner.

3.1 External rollout posture

  • Make the external experience feel clearly deliberate and production-ready.
  • Decide which interactions are visible by default and which remain advanced.
  • Ensure the outward rollout exposes value quickly without breaking the proven internal workflow.
  • Keep the external surface compatible with the object catalog and metadata model built earlier.
  • Define what users should see first when entering a project.

3.2 Renderer and visualization expansion

  • Treat Pixi as a serious rendering option with real performance and fidelity goals.
  • Define what workloads Pixi should handle better than the current editor path.
  • Plan for advanced canvas interactions and richer rendering primitives.
  • Keep Pixi separated from the map editor so each can evolve independently.
  • Identify how Pixi could support future visualization or simulation features.
  • Capture where Pixi should stay experimental and where it should become production-ready.
  • Establish how future rendering layers inherit from the same catalog and workspace data.
  • Keep photo-backed and generated assets compatible with the rollout path.

3.3 2.5D and spatial evolution

  • Define what 2.5d means in product language.
  • Treat 2.5d as a bridge toward more spatial presentation, not a dead-end mode.
  • Identify whether depth, tilt, layering, or perspective effects add user value.
  • Keep the option open for future 3D-style spatial experiences where they improve comprehension.
  • Prevent the editor from becoming locked into a flat-2D-only mental model.
  • Use 2.5D as the transition layer between generated assets and richer 3D rollout.

3.4 Exit criteria

  • External users can enter the product through a production-ready experience.
  • The rendering architecture can serve generated, photo-backed, and 3D assets.
  • 2.5D remains available as a bridge, not a dead end.
  • The rollout path is stable enough for broader public use.

3.5 Risk flags

  • External rollout hides instability instead of exposing value.
  • Pixi becomes a side quest rather than a strategic renderer.
  • The catalog data model cannot support both photo-backed and 3D assets.
  • The external experience arrives before internal confidence is real.

3.6 Must-not-slip items

  • The outward-facing experience is production-ready before release.
  • Pixi has a defined future and the editor/renderer story stays separated.
  • 2.5D remains a bridge.
  • The rollout path is stable enough for broader public use.

What I envision#

  • One coherent product instead of scattered plan fragments.
  • A workspace that feels built for real operators.
  • A serious control plane for admin and permissions.
  • Pixi and the engine layer treated as strategic, not incidental.
  • A path from 2D to 2.5D and eventually deeper spatial presentation where useful.
  • The main site living as a Next.js + React surface.
  • Archived reference material preserved only as history, not as a planning source.

Reference rebuild rule#

Do not recreate the old reference layer until the overhaul actually needs a fresh canonical reference set.

If it returns, it must be rebuilt from this plan and current source truth, not copied from archived docs.
